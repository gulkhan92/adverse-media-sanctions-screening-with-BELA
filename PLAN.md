# Adverse Media and Sanctions Screening Platform

Implementation plan using BELA and BLINK for multilingual entity linking.

Working product name: `BRAND_NAME` (default "Atlas Screening"; run a trademark check before any public launch).
Team: 1 to 2 full-stack engineers with ML experience. Duration: about 14 weeks.

## 1. Writing and engineering conventions (mandatory)

- Use a professional, neutral tone in every artifact: code comments, commit messages, docs, issue titles, UI copy, marketing copy. No slang, jokes, emojis, or hype wording.
- Never mention any AI assistant, chatbot, or AI vendor tool by name in code, comments, docs, commit messages, or UI copy. No "generated by" notes.
- Never use the em dash character (Unicode U+2014) anywhere. Use a colon, comma, parentheses, or a plain hyphen. Add a CI step that fails the build if U+2014 appears in any tracked text file.
- Every claim in the UI or marketing pages must be backed by a measurement produced in this repository or by a cited public source. No invented customers, customer logos, testimonials, awards, press mentions, or certifications. Scenario cards must be labeled "Illustrative scenario".
- Conventional Commits, pull request template, architecture decision records in `docs/adr/`.
- Python: type hints everywhere, `ruff`, `mypy` (strict on core packages), `pytest`. TypeScript: strict mode, ESLint, Prettier. Backend core logic coverage of at least 80 percent.

## 2. Scope and constraints

**Product.** A web platform where compliance teams screen people and organizations against sanctions lists, politically exposed person (PEP) data, and multilingual news. Entity linking connects names in news text to canonical entities so analysts review real risk instead of name collisions.

**In scope:** single and batch screening, continuous monitoring, alert queue, case management, entity network graph, operational analytics, platform revenue analytics, authentication and authorization, marketing website.

**Out of scope:** real payments, real customer data, legal determinations, production compliance certification.

**Constraints**
- Free and open-source tooling only. Any LLM runs locally and is a 3B to 4B model from Hugging Face.
- OpenSanctions bulk data is CC BY-NC 4.0 and compliance screening inside a business counts as commercial use. Use official government lists (OFAC) as the primary watchlist. Treat OpenSanctions as an optional non-commercial demo source only.
- All tenants, subscriptions, invoices, and revenue figures are synthetic. The UI must show a visible "Demo data" label wherever they appear.
- Matches are leads for human review, not determinations. Show this disclaimer on every screening result and report.


**Pipeline rules**
- Mention detection and linking run once at ingestion time and results are stored. Screening requests read stored results, so single-name screening stays fast. Only ad hoc "paste text" screening runs models live.
- Mentions that BELA rejects (no knowledge base entity) are kept as unlinked mentions (NIL). Private individuals rarely exist in Wikidata, so unlinked mentions are matched to subjects by name embedding, fuzzy score, and context attributes.
- Article content is untrusted input for the local LLM (prompt injection risk). See section 9.

### 5.3 Dataset build order and checks

1. `make data` runs all download scripts, writes `manifest.yaml` hashes, and prints row counts.
2. `make etl` produces `data/processed/*.parquet` and loads PostgreSQL.
3. Data quality tests (pandera and SQL assertions): no null names, valid ISO country codes, no duplicate watchlist keys, alias counts, QID coverage percentage per source, vector dimension equals 1024.
4. `make seed` loads `data/seed/` (demo tenant, users, subjects, monitored list, first 90 days of alerts) so a fresh clone shows a populated product.

### Phase 3: Entity linking engine, hybrid router, and evaluation (weeks 3 to 5)

This is the core of the project. Build it as services plus a pipeline library.

**Services**
- `services/nel`: loads BELA once, exposes `POST /v1/link` with input `[{id, text, lang}]` and output per mention: `start`, `end`, `surface`, `qid`, `md_score`, `el_score`, `candidates[{qid, score}]` (top 10). Also exposes `POST /v1/embed` for bge-m3. Batch requests, fp16, request queue with backpressure, `/health` and `/metrics`.
- `services/blink`: `POST /v1/rerank` with input `{context_left, mention, context_right, candidates[{qid, title, description}]}` and output scores per candidate from the cross-encoder. English only.
- `services/llm`: llama.cpp server, chat-completions HTTP endpoint on an internal network only. A thin client in the API package enforces JSON-schema outputs, temperature 0, token limits, timeouts.

**Pipeline (worker tasks)**
1. Chunk articles to the encoder's maximum length (read it from BELA's config) at sentence boundaries with small overlap.
2. Pre-filter: bge-m3 topic classifier or keyword prefilter to skip clearly irrelevant articles (cost control). Measure recall loss on the gold set.
3. BELA link. Keep spans with `md_score` above the mention threshold. Decision routing (initial values, calibrate on the gold set):
   - `el_score` at or above 0.70 and top-1 margin at or above 0.15: accept.
   - `el_score` between 0.40 and 0.70, or margin below 0.15: adjudicate.
   - below 0.40: NIL (unlinked mention).
4. Adjudication: English text goes to BLINK cross-encoder over the top 10 BELA candidates (candidate text is the English Wikidata label plus description). Non-English text goes to the local LLM, which receives the sentence, the mention, and 5 candidates with descriptions and must return `{choice: qid | NIL, confidence, reason}`. Combine scores with a small logistic model trained on the gold set. Log every candidate and score in `mention_candidates` for the analyst transparency panel.
5. Type filter: keep persons and organizations using the Wikidata class hierarchy.
6. NIL handling: for unlinked mentions, compute bge-m3 name similarity, rapidfuzz token-set ratio, and context attribute agreement (country, role) against subjects and watchlist aliases. Emit a match only above a calibrated threshold and mark it "name-based, unlinked".
7. Adverse classification: the local LLM labels the evidence sentence with a category (fraud, corruption and bribery, money laundering, sanctions evasion, terrorism and extremism, organized crime, regulatory action, other, none) and severity (1 to 4), with JSON-schema output. Content from articles is wrapped in delimiters and treated as data only.
8. Calibration: fit isotonic or Platt calibration per route so reported confidence is meaningful. Produce reliability plots.
9. Alert narrative: the LLM writes a two to three sentence factual summary using only the stored evidence fields. A validator rejects any summary that includes names, numbers, or claims not present in the evidence.

**Baselines and evaluation harness** (`make eval`)
- Baselines: RapidFuzz name matching with no linking; BELA alone; BLINK alone on English; hybrid.
- Datasets: Mewsli-X (per language), the gold set (per language), a collision subset.
- Metrics: mention detection F1; linking micro-F1 and accuracy at NIL; recall at 1, 5, 10 of candidate retrieval; false positive reduction against RapidFuzz at equal recall for watchlist matching; throughput (passages per second); p50 and p95 latency; fraction of mentions routed to adjudication; LLM adjudication accuracy.
- Output `docs/eval/report.md`, a CSV per run, and `public/metrics.json` consumed by the website.
- Initial targets (confirm or revise with evidence): hybrid improves linking F1 by at least 5 points over BELA alone on the ambiguous subset; at least 50 percent fewer false watchlist matches than fuzzy matching at equal recall; BELA stage at least 20 passages per second on the target GPU (the BELA paper reports 53 samples per second on a single GPU); adjudication needed for at most 15 percent of mentions.

Deliverables: three services, pipeline library, tuned thresholds in versioned config, evaluation report, model card (`docs/model_card.md`) describing training data, intended use, limits, and known failure modes.
Exit: evaluation report committed; thresholds and calibration frozen as `nlp_config_v1`; 10,000 article throughput test passes.

### Phase 5: Screening workflows, scoring, cases, and graph (weeks 6 to 7)

Tasks
1. **Single screening:** resolve the subject (exact identifiers, name and alias vector search, trigram search, attribute checks for birth date and country), retrieve watchlist matches and linked adverse media mentions, compute scores, store `screening_matches` with feature breakdown for explainability.
2. **Risk score** (configurable, versioned, editable by tenant admins within bounds):
   `score = 100 * (0.40 * list_weight * match_confidence + 0.35 * adverse_severity * link_confidence + 0.15 * recency_decay + 0.10 * source_reliability)`
   Default list weights: sanctions 1.0, PEP 0.6, adverse media only 0.4. Levels: critical at 80 or above, high 60 to 79, medium 40 to 59, low below 40. Show each component in the UI.
3. **Batch screening:** CSV upload (up to 10,000 rows) validated with a downloadable template, processed asynchronously with progress, partial failure report, and result export.
4. **Continuous monitoring:** a scheduled task checks new mentions and watchlist updates against monitored subjects and creates alerts, de-duplicating by subject, article, and list entry.
5. **Alert lifecycle:** statuses `new`, `in_review`, `escalated`, `true_match`, `false_positive`, `closed`; assignment, comments, mandatory reason on closure, every change in `alert_events`. Reviewer decisions feed `alert_stats_daily` and a labeled feedback table for later evaluation.
6. **Cases:** group alerts and entities, notes, status, due date, owner.
7. **Graph service:** combine `entity_relationships` (GLEIF parent and child, Wikidata ownership, ICIJ relationships) with article co-occurrence edges (same sentence, weighted). Provide neighbor expansion (depth up to 3, cap 500 nodes), shortest path between two entities, and edge provenance. Use networkx on extracted subgraphs.
8. **Reports:** PDF screening report (subject summary, matches, evidence excerpts with source links, score breakdown, reviewer decision, disclaimer, timestamp, report ID) using WeasyPrint.

Exit: end-to-end test: create subject, monitor it, ingest a fixture article, alert appears via SSE, analyst resolves it, report exports.

## 10. Security, authentication, and authorization specification

**Authentication**
- Passwords: Argon2id with tuned parameters, minimum 12 characters, zxcvbn strength check, common password rejection, no composition rules that reduce entropy.
- Login protection: per-account and per-IP rate limits, progressive delay, temporary lockout, generic error messages, audit entries for failures.
- MFA: TOTP (pyotp) with QR enrollment, 10 single-use recovery codes stored hashed. Mandatory for platform admin and tenant admin roles.
- Tokens: short-lived access JWT (10 to 15 minutes, EdDSA) held in an httpOnly, Secure, SameSite=Strict cookie. Refresh tokens are opaque random values stored hashed, rotated on every use, with reuse detection that revokes the whole session family. Absolute session lifetime and idle timeout configurable.
- CSRF: double-submit token for state-changing requests; the web app proxies `/api` to keep a single origin.
- Password reset: single-use, time-limited, hashed tokens; no account enumeration.
- API keys: random prefix plus secret, stored hashed, shown once, scoped to specific permissions and tenant, with expiry and last-used tracking.

**Authorization (RBAC with tenant scoping)**

| Permission | viewer | analyst | manager | tenant admin | finance analyst | platform admin |
|---|---|---|---|---|---|---|
| View alerts, entities, graph | yes | yes | yes | yes | no | yes |
| Run screenings, resolve alerts | no | yes | yes | yes | no | yes |
| Manage cases | no | yes | yes | yes | no | yes |
| View operational analytics | no | no | yes | yes | no | yes |
| Manage users, API keys, risk config | no | no | no | yes | no | yes |
| View audit log (tenant) | no | no | no | yes | no | yes |
| View platform revenue | no | no | no | no | yes | yes |
| Manage tenants and platform settings | no | no | no | no | no | yes |

Enforce on the server with dependency-injected permission checks and PostgreSQL Row Level Security. The frontend hides unavailable actions but never relies on hiding for protection. Add automated tests for every role against every endpoint group and for cross-tenant access attempts.

**Data protection**
- TLS 1.2 or higher everywhere with HSTS. Encrypted disk volumes for the database host. Column-level encryption with pgcrypto for personal identifiers (date of birth, identifiers) in subject records. Keys loaded from environment secrets, never committed.
- Data minimization: store snippets and extracted entities, not full article text. Retention settings per tenant with a scheduled purge job. Soft delete plus scheduled hard delete for subjects on request.
- Logs must never contain passwords, tokens, or full personal identifiers. Structured logs with request IDs.
- Tamper-evident audit log: append-only table with a hash chain, verification job, no update or delete permission for the application role.
- Security headers: strict Content Security Policy, X-Content-Type-Options, frame protections, Referrer-Policy, Permissions-Policy. CORS disabled by default (same-origin).
- Dependency and image hygiene: pinned versions, lock files, Trivy and gitleaks in CI, non-root containers, read-only file systems where possible, internal-only networks for the database, queue, and model services.

**LLM and pipeline safety**
- Treat all article text as untrusted. Wrap it in explicit delimiters, instruct the model to treat it as data, constrain output with a JSON schema, disable tools and network access for the model, cap token counts, and validate outputs before storage.
- The LLM never makes the final clear or flag decision alone. Its outputs are inputs to the score and are always shown with the evidence.
- Record model name, version, prompt version, and configuration version on every stored decision.
- Fetcher safety: block private IP ranges (SSRF protection), enforce response size and time limits, sanitize extracted text.

**Responsible use**
- Disclaimers on results and reports; reviewer decision required before any outcome is final.
- Bias and error analysis (names by language and script, common names) documented in `/methodology` and `docs/model_card.md`.
